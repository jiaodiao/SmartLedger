## 已实现且合并时应保留的定制

### C01 监听状态磁贴（2026-10-22；提交 220bb23）

用户需要关闭不想长期展示的后台通知后，仍能在控制中心查看真实的监听状态。

- 保留名为“智能记账”的快捷设置磁贴，点击仅打开应用，不切换监听开关。
- 保留四种状态：“监听正常”“正在恢复”“未开启监听”“状态未知”。
- 不能只凭通知使用权已开启或历史缓存，就显示监听正常；应使用当前进程确认的连接信息。监听服务销毁后标记未知，避免假正常。
- 打开控制中心获得刷新机会时重新判断，连接变化时尽可能刷新；不承诺系统杀进程瞬间更新，也不因长期没有支付通知就认定异常。
- 保留“我的 → 设置 → 自动记账 → 添加状态磁贴到控制中心”，Android 13+ 调用系统添加接口，并显示系统返回结果。OriginOS 上只依靠手动查找磁贴曾无法找到，因此不能删除此入口。
- 保留原有前台保活、自动重连、开机恢复及收支、待确认、监听异常通知。用户在系统设置中单独关闭“后台自动记账”通知类别，代码不强行取消前台服务通知。

主要位置（以下 Kotlin 路径均相对于 `app/src/main/java/com/smartledger/`）：

- `service/ListenerTileService.kt`、`service/ListenerStatus.kt`。
- `service/PaymentNotificationListener.kt` 的连接、断开、销毁处理。
- `ui/settings/SettingsScreen.kt`、`app/src/main/AndroidManifest.xml`、`app/src/main/res/values/strings.xml`。

验证边界：已构建并检查 Manifest、签名；尚无最终真机证据证明磁贴在目标设备上完整可用，不能把源码注册成功当成 OriginOS 验收通过。

### C02 主界面隐藏最近任务卡片（2026-10-22；提交 220bb23）

- `MainActivity` 保留 `android:excludeFromRecents="true"`。
- 桌面图标、磁贴仍能打开应用；隐藏任务卡片不停止通知监听，不另建任务管理或保活机制。
- 用户当时使用 vivo X100s / Android 16 / OriginOS 6，已反馈最近任务隐藏生效。
- 不把此需求扩展为隐藏系统后台服务管理信息。

主要位置：`app/src/main/AndroidManifest.xml`。

### C03 应用从用户自己的 GitHub 仓库更新（2026-10-29；提交 6f69031）

- `util/UpdateChecker.kt` 中 `REPO` 必须继续为 `jiaodiao/SmartLedger`，不能被上游版本覆盖回作者仓库。
- 保留启动检查和设置内手动检查、现有下载及安装流程；手机安装仍需系统确认，不承诺静默安装。
- 包名保持 `com.smartledger`，沿用已安装定制版的签名，后续版本号递增，保留用户数据。
- 必须沿用的证书 SHA-256：`327e32915727b6059f303afdee1017ec3d5f34f8cd93bada721f92248b09df9a`。
- 不生成新调试密钥代替原密钥；云端构建也必须使用相同签名。密钥、密码、令牌不能进仓库。
- 显示版本采用“对应上游版本.定制修订号”；`versionCode` 高于已发布和已使用的版本，不能直接被上游数值覆盖回退。
- 不以卸载、清数据或破坏性数据库迁移解决升级问题。早期首次测试曾允许不迁移作者版旧数据，这个历史许可不适用于现在的日常更新。

主要位置：`util/UpdateChecker.kt`、`app/build.gradle.kts`、[定制版更新说明](custom-updates.md)。

历史证据：用户已确认安装 1.0.28.1；后来 Git 历史显示已合并上游 v1.0.31。以前的 Grok 配置讨论只是方案，本记录不据此声称云端自动化已创建或完整验证。

### C04 分类颜色可编辑，色板扩为 18 色（2026-10-30）

用户发现已有分类不能改颜色，多个分类颜色重合；新增时原有 6 色也不够。

- 新增、编辑分类共用 18 色色板，分三行展示，选中色有勾选标记。
- 编辑时可同时修改名称和颜色，默认带入原值；不主动重分配已有分类颜色。
- 分类管理列表中的图标及浅色背景使用分类实际颜色，方便发现重复。
- 编辑保存原分类的 ID、类型等属性，只更新名称和颜色；不改数据库结构。

主要位置：`ui/category/CategoryManageScreen.kt`。

### C05 明确导入入口，修正重复备份误报失败（2026-10-30）

用户确认理解导出与备份用途，但要求导入有明确入口；实际使用中发现恢复与现有数据相同的备份会误报“格式错误或为空”。

- “我的 → 数据备份”改为“导入与备份”。“数据导出”仍独立保留。
- 页面固定显示“立即备份”和“导入账单 CSV”，不能因为存在备份就把选择文件入口替换成恢复按钮。
- 历史备份每份保留独立的恢复、删除操作。
- 导入前说明：目前支持本应用导出的账单 CSV，不保证直接兼容微信、支付宝原始账单；仅追加、不清空或覆盖已有账单，重复记录跳过。
- 选文件后先预览文件名、可新增笔数、重复笔数、格式异常行数；确认后才写入，取消不写入。
- 全部重复时提示“没有新增账单，记录均已存在”，不能当作失败；混合数据分别报告新增、重复、异常数量。
- 空文件、仅表头、格式不支持、无有效记录、读取失败和写入失败分别给出原因。
- 预览保留当时读取的文件内容；确认写入时重新对当前账单去重，防止期间新增的账单重复导入。
- 写入在数据库事务中进行，写入失败整批回滚，不留下半批导入。
- 延续原有去重条件：金额按分比较、收支类型及商户一致，时间相差不超过一秒；文件内部重复也跳过。不要把它与自动记账的跨渠道去重规则混为一谈。
- 正确读取 BOM、CSV 转义双引号、逗号和引号内换行；严格校验日期、时间、类型与有效正数金额，不把错误日期替换成当前时间。
- 导出分类名称也做 CSV 转义；备份历史按逻辑账单统计，避免备注换行导致记录数虚增。
- 文件分类名称在现有分类中不存在时归入同类型“其他”；不自动重建自定义分类及颜色。
- 页面明确：备份只包含账单，不包含分类颜色、预算及应用设置，不能称为完整应用备份。重装后的首页恢复路径也使用同一套结构化结果提示。

主要位置：`ui/backup/BackupScreen.kt`、`ui/profile/ProfileScreen.kt`、`MainActivity.kt`、`util/CsvImporter.kt`、`util/CsvImportData.kt`、`util/CsvExporter.kt`、`util/BackupStorage.kt`。

测试：`app/src/test/java/com/smartledger/util/CsvImportFormatTest.kt`。

### C06 最近识别详情诊断入口（2026-10-30）

用户怀疑微信通知只包含渠道和金额，虽然微信内部账单能看到商家；因此先诊断通知实际内容，再决定如何增强识别。

- 入口：“我的 → 设置 → 自动记账 → 最近识别详情”。
- 记录开关默认关闭，开启后只记录后续支付相关通知，最多保留最近 30 条，最新在前；关闭停止记录，旧记录仍可看，支持清空。
- 列表显示收到时间、渠道、通知摘要和通知当时的处理结果。
- 详情分别显示原始标题、普通/展开正文、分行内容等原始字段；缺失字段写“未提供”，另显示实际用于识别的文本。
- 分组摘要采用子通知补全时，原始字段与补全子通知字段分开展示。
- 展示当前流程实际产出的金额、收支类型、商家、支付渠道、分类，以及已入账、待确认、重复跳过/合并、过滤或识别失败原因。
- 只标记“未提取到商家”，不能仅凭提取结果断言通知原文没有商家；未运行解析或未产生分类结果时也不凭空补结果。
- 普通微信聊天不收录。微信来源按明确支付服务标题筛选，不能仅因聊天正文提到“微信支付”或金额就保存；来源不明确的微信综合摘要不收录。补全子通知也检查来源，不安全则丢弃该诊断记录，原有记账流程继续。
- 原文只在本机 `noBackupFilesDir/payment_diagnostics.json` 保存，排除系统备份及账单导出/备份；不自动上传、不新增云端服务。
- 支持“复制本条详情”，由用户检查、隐去隐私后主动分享；超长字段截断并标注，不把截断伪装成微信原文。
- 清空后旧异步回调不得重新添加记录；被 30 条上限淘汰的记录也不能被旧回调补回。
- 诊断只是旁路记录，不修改现有通知识别、商家提取、自动分类、去重、确认或入账决策。待确认是当时的通知处理结果，后续手动确认以账单为准。
- 空列表提示开启后等待下一条支付通知，无法补回过去的通知。

主要位置：`service/PaymentDiagnostic.kt`、`service/PaymentDiagnosticStore.kt`、`service/PaymentNotificationListener.kt`、`ui/settings/PaymentDiagnosticScreen.kt`、`ui/settings/SettingsScreen.kt`、`MainActivity.kt`。

测试：`app/src/test/java/com/smartledger/service/PaymentDiagnosticTest.kt`。

## 本次已讨论但未实施的功能

- 进一步增强商家提取和自动分类：等待真实诊断内容，判断是微信没有提供商家，还是当前提取规则不足。本轮没有增加新的商家正则或分类关键词，也没有把通知原文自动作为分类输入。
- 直接读取微信内部的支付详情页、历史消息或详细账单：当前只有通知监听能力，不具备直接读取微信私有数据的能力；没有增加无障碍、屏幕识别、Root、Hook 或微信账单接口。
- 直接导入微信/支付宝导出的原始账单、完整应用备份：未实现，不能在合并或发布说明中当成已有能力。
- 对无商家、无商品说明、仅渠道和金额的通知，不应通过猜测虚构商家或类别。

## 给合并上游的 AI / Grok Bot

1. 先读本文件和 `custom-updates.md`，检查最新源码、Git 历史和 Release；文件名可以调整，但必须保留对应用户行为。
2. 从用户最新主分支合并上游目标提交，不用作者目录直接覆盖用户仓库，不强制推送。遇到功能冲突，逐项对照 C01～C06，不能机械地全选上游或全选本地。
3. 特别检查 `MainActivity.kt` 的诊断路由及恢复结果、`SettingsScreen.kt` 的两个定制入口、Manifest 的磁贴与最近任务隐藏、`UpdateChecker.kt` 的用户更新源。
4. `PaymentNotificationListener.kt` 同时承载上游去重修复和定制状态/诊断，保留双方逻辑；不要为了保留诊断而回退上游 v1.0.31 的防重复和连续同金额交易修复。
5. 涉及数据库时检查正确迁移，不删除数据解决冲突；本轮 C04～C06 未改变数据库表结构。
6. 对照 C01～C06 的行为验证，并运行与改动相称的测试和编译；若上游提供等价或更好的实现，可以整合，但明确记录对应关系及验证结果。
7. 不把“已编译”“测试通过”“APK 签名一致”写成“已真机验收”。当前磁贴仍有设备确认边界；本次颜色、导入和诊断未完成手机实测。
8. 发布由用户安排的 Grok Bot 执行，遵守版本、包名、签名和用户仓库更新源要求；缺密钥、迁移不明确、冲突无法判断或验证失败时报告原因，不能发布不确定结果。
9. 后续每次用户定制同步更新本文件：需求、最终行为、位置、测试/真机状态及未实现事项，避免记录逐渐失真。不要自动实施本文件中的未实施功能。
